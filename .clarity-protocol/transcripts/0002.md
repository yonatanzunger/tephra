## The three types: agree, but it bundles two things worth separating

Your framing is right and it's a real sharpening — three UXes is a countable scope number in a way "small number of views" wasn't. But "native file type" bundles *type* (how a file is named, parsed, merged) with *syntax* (what's actually in the bytes), and those can be split.

Portal found a genuine bug here worth inheriting: a mutable side list that got typed as an append-only notebook file merged with append-union semantics, which **silently duplicates edited lines** — no error, the file just quietly fills with near-duplicate paragraphs. The lesson is that types must be **explicit and declared by name**, not inferred from extension or context.

But that argues for three declared types, not three syntaxes. I'd propose: **one syntax family — markdown, leniently parsed — with three declared types over it.** The TODO file is markdown that a plain reader finds sensible, even though you only ever *see* it through the TODO UX. That costs the TODO UX some freedom (it has to round-trip a markdown document, not a bespoke format) and buys three things: the exit stays structural rather than aspirational, there's one parser and one merge story instead of three, and — the sequencing argument, which I find the most persuasive — **v1 has no TODO UX, so during v1 and v2 your TODO list simply *is* a hand-edited markdown file.** If v3's TODO type is markdown-shaped, v3 opens that file. If it's a distinct syntax, you migrate.

**The one thing missing from the count of three:** the subject/search view. A subject view is a filtered assembly of ranges from many .md files, and it's the view that tests the central bet of the whole design. If it's read-only, it folds into the .md UX and the count stays at three. If it's *editable*, it's a composite surface writing back into source ranges — which is the most technically demanding thing in the design and it doesn't appear anywhere in the type list. Worth deciding deliberately rather than discovering.

## "Cache" is the wrong word, and the difference is a data-loss bug

I agree with the substance — local directories over a network source of truth — but the word matters here, because caches have a specific safety property: **a cache may be discarded and refilled from truth.** That's exactly false for this. Between writing on the plane and pushing on landing, the local copy is *the only copy*. The correct name is a **local replica with write-back**, and the distinction is load-bearing the first time something goes wrong and some recovery path thinks "just refill from the server."

Except — and this is where your instinct is exactly right — **for attachments.** Twenty years of markdown is a few hundred megabytes; twenty years of PDFs and pasted images is not, and the phone will feel that first. So there are two disciplines in one directory: **text is a replica** (never evictable until pushed), **blobs are a genuine cache** (evictable, refetchable from truth). That's a real design consequence, and it means the phone can hold the whole corpus of *thinking* without holding the whole corpus of *material*.

Two other things your statement decides that are worth making explicit:

- **It's a topology decision, not a reconciliation decision.** A star with a hub eliminates peer-to-peer and local-network-only sync. ## The split isn't quite an implementation detail — and that's an argument *for* day files

I agree with the abstraction: the app should see one document, and "very large files get unwieldy" is the honest reason for splitting. But the split is visible to one thing above the storage layer — **merge operates on files.** Which means if the split point is chosen at runtime by size, two devices writing the same day will chunk it differently, put the same content into differently-shaped files, and manufacture divergence out of nothing.

So the split rule has to be **deterministic and content-derived**, identical on every device. Date boundaries are the obvious such rule, and they have a second virtue: a day file is append-only, an arbitrary chunk is not, and append-only is exactly what licenses the cheap append-union merge. So day files aren't a workaround for file size that we're stuck with — they're the split rule that makes concurrent editing tractable, and the file-size benefit is a bonus.

The abstraction survives intact. The correction is just that the boundary sits in the **format**, not in the storage class's discretion.

Two consequences worth knowing now: the logical document has to be **lazy and windowed** regardless (twenty years of prose is tens of megabytes, which no editor handles joyfully at 130 WPM — so you'd never load it whole even if it were one file), and it has to supply **addresses that survive both the window moving and a merge**. Byte offsets into a logical concatenation don't: an upstream insertion from the phone shifts everything after it. ## Dates and tags: unify the query, not the data

I worked this one carefully because your own carried rule says take a generalization exactly as far as it deletes concepts — and I don't think this one pays at the data layer. They're alike in query surface and unalike in five ways that all bite:

- **Every character has exactly one date; most text has no tags.** A date is a function of position, a tag is a relation.
- **Dates are ordered and support range queries.** Tags are set membership. Merging means either tags carry unused ordering machinery, or dates lose ranges.
- **Dates determine the storage split.** Tags can't — they overlap freely, which is the exact property that made subjects-as-tags beat notebooks-as-containers.
- **Dates are system-assigned and immutable.** Retagging is a core gesture (R12); re-dating is corruption.
- **Dates are contiguous and non-overlapping.** Tags aren't.

Unifying wouldn't delete a concept; it'd rename one and add a footnote with five exceptions.

**But there's a real unification underneath, and it's at the view layer** — which is where the scope number lives, so it's the one that counts. A subject view, a date-range view, and a search result are all *a filtered assembly of ranges from the stream*. Rewriting a day file per keystroke isn't cheap. **An append is** — and the notebook is append-shaped anyway, which is the same property that makes its merge rule work, so a journal isn't foreign machinery here. Two candidates:

- **Durable-on-append** — keystrokes append to a journal in main, the day file is rewritten on quiescence, a crash replays. Satisfies "losing anything, ever" literally.
- **Durable-on-quiescence** — debounced autosave, no journal. Loses the last few hundred milliseconds. Satisfies R1.2 psychologically and violates it literally.

They're API-compatible, so **the choice can be deferred but the contract can't**: state it now as *durable when `flush()` resolves, durable within N ms otherwise*. Fixing N later is not a breaking change; discovering there was never a contract is.

## What CodeMirror actually gives you

The core is **`@codemirror/state`**, which has no DOM dependency — it's a rope, a transaction system, and a state container that happen to be maintained alongside an editor.

- **`EditorState` is immutable.** `state.update(spec)` returns a `Transaction` whose `.state` is the successor. A view dispatches transactions; a headless state accepts them identically.
- **A change spec is `{from, to, insert}`, or an array of them — relative to the pre-state, required to be sorted and non-overlapping.** That is `replace([{span, payload}])`, arrived at independently and matching exactly.
- **`ChangeSet`** can be inverted, composed, mapped through other changes, and serialised (`toJSON`/`fromJSON`).
- **`history()`** (in `@codemirror/commands`) is a StateField observing transactions, grouping by a configurable delay and by `userEvent` annotation. Transactions opt out with the `addToHistory` annotation, or force an event boundary with `isolateHistory`.
- Positions are UTF-16 code units throughout.

## The reframing

**Nothing durable holds an offset — D11 already guarantees it.** Bookmarks and tags are markers in the text, section entries reference names, links resolve by lookup. The *only* serialised offsets anywhere are inside the journal, which is a transient WAL discarded at quiescence, written and read by one build of one app.

The question is only whether a number's semantics are "count of UTF-16 code units" — which is invisible in the file and irrelevant outside the process that wrote it.

**The document↔storage boundary is file-granular, not offset-granular.** Writes are whole-file atomic replacements; reads load whole files. At ~100 KB a day, nothing ever seeks into an undecoded file. So byte offsets are never *required* as an addressing unit — bytes appear only in operations that take no offsets at all.

Together those remove most of the case for bytes and most of the case against UTF-16.

The structural fact underneath: **conversion is nearly free when it's a byproduct of a bulk transcode you're already doing** (decode on load, encode on save), and expensive when it must be maintained incrementally against a buffer being edited at 130 WPM.

## Generation as the rewind coordinate — yes, and it pulls in a Portal insight

Generation does advance on every change, and making it the rewind coordinate is right. Two things fell out that are better than what we had:

**Grouping stops being part of the primitive.** `rewindTo(generation)` is character-granular; `undo` becomes *rewind to the generation at the previous history-group boundary*, where grouping is policy over `EditOrigin` and adjacency. ## There are three positions, not two

- **A — journal local.** Files are truth, journal is a WAL. Undo per-device. Rewindable history homeless.
- **B — journal authoritative and synced**, files materialised from it.
- **C — files authoritative, journal synced alongside as supplementary history.**

So it's neither the truth nor a projection of the truth: an independent second record that must be kept in agreement with the first, across devices. ## B deserved a better hearing than D23 gave it

I rejected journal-as-truth on the grounds that it demotes plain files to an export. **Git is the counter-example** — its history *is* authoritative, its working tree *is* a checkout, and the exit is excellent because the files are always sitting there as ordinary files. **What actually kills B here is hand-editing.** Under B, a hand-edit is invisible to the authoritative history: the next materialisation either overwrites it or diverges from it. | *Undo what I just did* | local journal | keystroke / edit-group | this device |

## And your conceptual objection is right, with a cheap fix

## The reframe that organises the comparison

## How it's organised

Not by where things came from, but by when you'll need them — and **every entry states the failure it prevents**, because a rule without a reason gets removed as an oddity by the next person to read the code.

**§1 — Invariants that fail silently.** The highest-priority group, because the code keeps running and something is quietly wrong. Watch directories not descriptors; stale positions throw; never rewrite a file you failed to parse; splice into original bytes rather than serialising from a model; parse markdown not regex (**including in v1's scan-based search**, which I'd previously described as "grep for markers"); echo suppression; `StoragePosition` never escapes; same-segment spans coalesce; quiesce before external mutation.

## The point of the class: your four options become a policy object

## Three things in the design you haven't seen yet

**The Secure Enclave requirement is load-bearing, not a preference.** An ordinary keychain item is included in a Time Machine backup. Shred a key, restore last week's snapshot, and the key comes back while the ciphertext — also backed up — becomes readable again. **The backup system would silently undo the deletion.** A Secure Enclave key is non-extractable, so it was never in the backup and can't return from one.

**A shred has to rotate the master key.** Removing an entry from the key table means rewriting the key table, and rewriting a file on a copy-on-write filesystem leaves the old version in orphaned blocks and snapshots — the original problem, recursed onto a smaller file. Rotating dissolves it: re-wrap the survivors under a fresh master, destroy the old one, and every stale copy of the table becomes undecryptable wherever it is. Same for the index, on every write.

**Three verification tests, and the third is the one nobody writes.** Shred-and-scan; then break the shred on purpose and confirm the test *fails*; then **snapshot, shred, restore, and confirm the content is still unreadable.** That last one is what catches a master key that turned out to be extractable — a failure that would otherwise surface years later, by accident, at the worst moment.

## 1. Marker parsing / serialization — `app/src/main/x/markers.ts`

**Syntax (the only regex that matters):**
```ts
const MARKER = /<!--tephra:(mark|tag-start|tag-end)[ \t]+([^\n]*?)-->/g
const ATX    = /^(#{1,6})[ \t]+(.*?)[ \t]*$/
```
So three real marker verbs — `mark` (a bookmark/anchor), `tag-start`, `tag-end` — plus ATX headings, which are ordinary text scanned as spans. There is no id field, no key=value attribute grammar: everything after the verb up to `-->` is a single trimmed **name**. Unnamed markers are dropped.

**Types:**
```ts
export type RawSpanKind = 'heading' | 'anchor' | 'tag-start' | 'tag-end'
export interface RawMarker {
  readonly kind: RawSpanKind
  readonly name: string
  readonly from: number   // offsets into the BODY (not the file)
  readonly to: number     // whole comment for markers; whole line for headings
  readonly level: number  // headings only
}
```

**Markdown awareness** is `codeRegions(body): readonly (readonly [number, number])[]` — fenced blocks (``` and `~~~`, honouring fence char/length/indent/info-string rules), 4-space indented blocks, and inline backtick spans with CommonMark's equal-length rule. `scanMarkers` skips any marker or heading whose start falls in a code region. The header comment is explicit that a plain regex scan would corrupt the notebook the moment you write *about* Tephra.

**Key functions:**
- `scanMarkers(body): readonly RawMarker[]` — document order.
- `subjectKey(name)` — case-insensitive, whitespace-normalised comparison key (duplicated deliberately in `app/src/shared/tags.ts` for renderer use).
- `resolveTags(markers, body): readonly ResolvedTag[]` where `ResolvedTag = { name, from, to, unterminated }`. Pairing relies on strict alternation per subject (no ids). Unmatched `tag-start` runs to end of segment; unmatched `tag-end` ignored. Spans are whitespace-trimmed.
- `resolveAnchors(markers): ReadonlyMap<string, RawMarker>` — first wins.
- `placeMarker(body, offset, marker): { at, text }` — **a marker never begins a line**, because a comment starting a paragraph's first line becomes a CommonMark HTML block and kills all inline formatting on that line. At a line start it backs up one char; at offset 0 or after a line whose meaning is its exact contents (`canAppendTo`: fences, thematic/setext rules, table rows, indented code) it takes its own line and appends `\n`.
- `markerRemoval(body, m): TextEdit` — a marker owning its own line takes the newline too, or one paragraph becomes two.
- `retagBody(body, ops: readonly TagOp[]): string` with `TagOp = { subject, range: {from,to}, op: 'add'|'remove' }`. Interval arithmetic: strip all markers of the involved subjects, union/subtract, re-emit. ## 3. Editor widget layer — `app/src/renderer/src/editor/widgets.ts`

Two mechanisms, forced by CodeMirror:
- **Inline** widgets: `inlineWidgets = ViewPlugin.fromClass(...)`, rebuilt per viewport via `buildInline(view): DecorationSet` on `docChanged || viewportChanged || selectionSet || rebuildWidgets` effect. Provides `EditorView.atomicRanges`.

Unrender-under-cursor:
```ts

  widgetOptions.revealAdjacent ? nearCursor(...) : overlapsCursor(...)
```
Inline constructs check `if (widgetOptions.reveal && overlapsCursor(...)) continue`; block constructs use `blockRevealed`, because replacing whole lines removes them from vertical layout and j/k would skip them.

## 1. What Tephra is

A single-user, self-built notebook app for a person who thinks *by writing* — where friction in the writing is a direct tax on thought quality. Core artifact: **one continuous chronological stream** of prose, equations, tables, and inline figures, automatically dated, always available on whichever device is at hand, and findable months later. Projects are not separate notebooks; **subjects are retrospective tags on ranges**, and a subject view is a filter over the one stream. Around that sit a TODO list ranked by urgency, pinned lists, an events calendar, and document collections ("filesets").

Named for tephrochronology — dating strata by ash layers. Extracted from **Portal** (`../portal`, paused not abandoned; see `/Users/zunger/src/tephra/.clarity-protocol/carried-over.md`), after the realization that the notebook was ">90% of the value."

The diagnosis is 20 years long and specific: era 1 (paper lab notebook) died on access; era 2 (structured paper notebook, TODO spread + calendar) worked *excellently* and also died on access; era 3 (Google Docs → M365) solved access and failed on fit/quality. **None failed for lack of features.** Hence: the target is *smaller* than "a high-powered notebook app."

Two distinctive threads: the **graveyard problem** — era 2's two-page TODO spread filled up, forcing live items to be transcribed forward and letting the rest die visibly; digital lists never fill, so that forced review never happens — and the **departer's exit**: plain durable files so 20 years of thinking is never hostage to whether this program still runs.

## 3. Scope

**The counting rule** (`goal/scope.md`): "**Tephra is a small number of view types over one directory of plain files**" — three native view types: **Markdown** (`.md`, the reading/editing surface — notebook stream, branched docs, pinned lists), **TODO** (seen only through the TODO UX), **Fileset** (a directory with a master index; entries are URLs, file pointers, and bookmarks into markdown). Everything else is *external* (PDFs, OS-opened) or *embedded* (images). One syntax family, leniently parsed. **Type is declared by name, not inferred** (Portal found the failure: mistyped mutable list merges with append-union and silently duplicates edited lines). Pinning is membership in a distinguished fileset (D10). The subject view is **not** a fourth type. Amended by **D46**: a second, *shreddable* notebook stores files encrypted so deletion is real — a different storage choice, not a fourth type.

**In scope:** main chronological notebook; subjects-as-tags-on-ranges; branching a range into its own linked, findable file; TODO with status/due date/links/groupings/last-touched timestamp; pinned lists + events calendar; filesets with URL snapshotting; Mac and Android; offline; margin comments (R27) and import-to-annotate (R28, docx/pdf/clipboard).

**Out of scope:** managing the work products themselves (code, drafts, contracts — the notebook *points at* them); replacing calendar/email/file manager; Portal's Spaces, launch manifests, environment reconstruction; **multi-user anything**.

## 1. What a "kind" is architecturally

`DocumentKind` is a discriminator on `DocumentMeta`, declared in `/Users/zunger/src/tephra/app/src/shared/document-api.ts`:

```ts
export type DocumentKind = 'stream' | 'markdown' | 'todo' | 'fileset'   // line 359
```

`Document` is the universal contract (full declaration in `document-api.md` and the live `shared/document-api.ts`): `id`, `meta`, `generation`, `isDirty`, `read(span, at?) → DocumentWindow`, `snap`, `advance`/`distance`, `spans(kind?)`/`spansAt`, `resolveAnchor`, `replace(edits, origin?)` (the one mutation), `rewindTo(gen)`/`undo`/`redo`/`history`, semantic sugar (`tag`, `untag`, `setAnchor`, `removeAnchor`, `branch`), `onChanged`/`onDiverged`, `mapPosition`, and lifecycle `flush`/`reload`/`release`. Per MC1, `extent()` and `dateAt()` were removed from `Document` into a stream-specific interface (`DocumentMeta & { kind: 'stream' }`, `isStream()` guard).

Main-side storage contract: `StoredDocument extends Document` in `/Users/zunger/src/tephra/app/src/main/x/documents/stored.ts` — `keys()`, `bodyOf(key)`, `setBodyOf(key, body, origin?)`, `titleOf(key)`/`setTitleOf(key, title)` (explicitly *not* an edit: no span, no undo entry, no generation), `setSourceOf`, `restoreTo(map)`, `useCreator(fn)`, `onJournal(...)`, `writeDirty()`.

Base class: `SegmentedDocument implements StoredDocument` (`main/x/documents/segmented.ts`) holds all generic machinery — segment map, edits, history, spans, comments, tags, journal. **Only two abstract members**: `protected abstract load(key: SegmentKey): Promise<Segment>` and `abstract keys(): Promise<readonly SegmentKey[]>` (plus abstract `id`, `meta`, `branch`, `importText`). A kind extends it when its content is "text with positions"; otherwise it implements `StoredDocument` directly. `SegmentKey` for one-segment documents is the constant `ONLY_SEGMENT` (`'content'`, D27).

Extension points — `architecture.md` fixes **four artifacts per kind**:

| Part | Where |
|---|---|
| the API | `shared/kinds/<kind>.ts` |
| the implementation | `main/x/documents/kinds/<kind>.ts` |
| the forwarder | `renderer/src/x/kinds/<kind>.ts` |
| the surface | `renderer/src/editor/kinds/<Kind>.tsx` |

Two renderer registries, both keyed by kind with markdown as *default rather than entry*: `renderer/src/x/kinds/registry.ts` (`forKind(info)`, `home(doc)`) and `renderer/src/editor/kinds/registry.ts` (`surfaceFor(kind)`, currently an empty `SURFACES` table). "A boolean varies a view; a file replaces one." Storage, sync, and history are **not** per-kind extension points — the design claim (file-documents.md) is "the kind varies what you can DO; it does not vary the architecture."

Access is mediated by `Corpus` (`main/x/documents/corpus.ts`), the single path from X to files:

```ts
use<T>(id, work: (doc: Document) => Promise<T>, how?: Borrow): Promise<T>
list(kind?): Promise<readonly DocumentId[]>;  exists(id);  create(id, kind);  rename(id, to);  remove(id)
interface Borrow { mode?: 'read' | 'write'  /* default write */; retain?: boolean /* default true */ }
```

Two guarantees: same object per id; valid for the duration of the borrow. Scoped borrow (not a leasable handle) so a dropped IPC close cannot leak. The map caches the *opening* (`Promise<Document>`), not the opened, to avoid the check-then-act race. Eviction: never dirty, never window-pointed-at, otherwise bounded LRU; `retain:false` never enters the cache. `layering.test.ts` asserts over the import graph that nothing outside `x/documents/` imports `w/notebook.ts`.

## 2. The concrete kinds

- **stream** (`kinds/stream.ts`, was `StreamDocument`, 83 members, ~13 day-shaped): segments are `DateKey`s (`YYYY-MM-DD`), grows at one end, adds `today()`, `dates()`, `extent()`, `dateAt()`, day splitting at 1 MB with prefix-stable boundaries, `removeSegment` override that knows a day can be several part-files. Demonstrated that "an infinite stream chopped into days is a file format, not a privileged thing."
- **markdown** (`kinds/markdown.ts`): one segment keyed by the constant, no whole-body date span. Adds nothing beyond `Document`. Demonstrated that everything already keyed by `SegmentKey` needed no second implementation.
- **fileset** (`kinds/fileset.ts`): body is an ordered list of typed markdown links. Adds `entries()`, `pin`, `unpin`, `reorder`, `remove` — each a `replace()` on a body span, so pinning inherits undo, write tiers, WAL, divergence, versioning. `reorder` is one batch so undo cannot land between delete and reinsert. Forced `shared/fileset.ts` to gain `scanEntries` (offsets) under `parseEntries`. Exposed a day-shaped bug in the base: `read()` walked keys by *adding days*; it now calls `segmentsAcross`.
- **external** (`kinds/external.ts`, MC6½): **one class for every kind**, for files outside the notebook (`isOutside(id)` = absolute path). Kind still comes from the filename so the right surface loads, but no kind verbs (all of them write). Read-only is on `DocumentMeta`, not a kind; enforced at three layers (`editable`, `readOnly`, transaction filter).
- **todo**: in the union, no implementation. **PDF: does not exist.** Deliberately excluded from MC ("adding one now would be testing the shape with an example instead of with the three kinds that already exist"). file-documents.md predicts the first non-text kind splits `Document` into a lifecycle contract (identity, dirtiness, flush, events, abstract undo) plus a text contract on top, since `read()` returns prose, `spans()` returns character ranges, and a position is a UTF-16 offset.

## 3. Storage and history

Plain markdown files, git-backed, no CRDT. Layout (`format-spec.md`): `notebook/stream/YYYY/MM/YYYY-MM-DD.md` (`.2.md` for split parts), `notes/`, `sections/_index.fileset.md` + `sections/<name>.fileset.md`, `attachments/YYYY/MM/`, `.tephra/` (never synced, disposable: `wal/<doc-id>.jsonl`, `index/`, `lock`, `issues.json`, `attachments.manifest`, `ui-state.json`). Type declared by filename suffix (`.md`, `.todo.md`, `.fileset.md`), mirrored in frontmatter `kind:`; frontmatter is authoritative. Writes are whole-file atomic replacements that **splice edited regions into the original bytes** — never serialize from a parsed model.

History is uniform across kinds, not per-kind. Two version axes that never convert: `SessionGeneration` (volatile number, owned by Document, the rewind coordinate for undo, dies with the process) and `VersionId` (durable string, a git commit, owned by History). `Repository` interface (`main/w/repository.ts`: `save`, `versions`, `contentAt`, `moveTo`) with `GitRepository` as the one implementation. WAL is per-document, seconds long, folded and truncated — explicitly not a second history. Write tiers: quiescence + ceiling, `flushAll()` over every dirty document, and the version tier calls `flushAll()` before committing. A commit and a restore are **corpus-wide**: MC7 made restore put back every document at that version and remove documents that did not exist then, routing each through `corpus.use` so open windows reset as the same act. Divergence is per segment, surfaced never auto-resolved (D12). Undo does not survive restart, deliberately.

## 4. Structured / non-prose

Nothing structured exists. Every kind is markdown text; the only structure is inferred, never stored: `TypedSpan = date | heading | anchor | tag` (plus `comment`), with **no ids** — "inference leaves nothing for one to identify." Markers are HTML comments (`<!--tephra:mark …-->`, `<!--tephra:tag-start/-end …-->`); paired point markers make overlapping tags expressible; same-subject spans may not overlap, which removes the need for identifiers.

Record-shaped kinds are named as future possibilities only (file-documents.md): "**todo / calendar** — record-shaped: an edit is a field, and history is per item"; "**a saved query or filtered view** — zero files; content is computed from other documents and writes are written THROUGH to them; there is no `load` and nothing to `writeDirty`."

The one index is `main/x/documents/corpus-index.ts` — a cache over what documents would say (D52), living *inside* the Corpus as part of the floor. It scans bytes and compares `stat` stamps rather than opening documents, precisely to answer "every subject in twenty years." A document answers about itself from its own segments and never consults it. Search and filtered views are M4; `.tephra/index/` is marked "(v2)".

## 5. Links

Forward links only. `tephra:` reference URIs (D53), one host per kind: `tephra:mark/<name>` (resolves by name, first in date order), `tephra:tag/<subject>`, `tephra:day/<date>`, `tephra:section/<slug>`; files and URLs stay ordinary relative paths / `https:`. Entry type is inferred from the link target, no type field. Trailing text after a link is the human-authored summary and regeneration must not clobber it. Dangling entries are shown dimmed and marked "not found", never hidden. Section nesting depth capped at three. Renderer link handling: `renderer/src/editor/kinds/markdown/links.ts`. A relative link resolves from **the document it is written in** — a real bug (MC5) where `../notes/offer.md` was resolved at day-file depth, so `from` is now part of the question.

No backlinks and no link index. `branch` writes the link into the stream only: "the link left behind in the stream is the relationship that matters, and it points the useful way. The reverse pointer is curious history" — the format spec's table says branch origin lives in *nothing*. `architecture.md` reserves the pattern: Document emits change events and Search subscribes, "so a second index later (backlinks, tags) needs no change to it."
